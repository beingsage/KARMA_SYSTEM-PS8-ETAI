# Output Contract and Result Model

The system produces a rich, structured document-knowledge result that is persisted to JSON and surfaced through the REST API.

## 1. Primary Output Envelope

The core output schema is defined in [app/schemas.py](app/schemas.py).

The main response object is `JobResult`, which exposes:

- `job_id`
- `status`
- `message`
- `uploaded_filename`
- `source_name`
- `source_type`
- `source_format`
- `parsed_source`
- `source_metadata`
- extracted text and document sections
- entities and relations
- layout and table data
- formulas and reading order
- ontology enrichment data
- graph summary and pipeline metadata

## 2. Key Result Sections

### Text and extraction
The final payload includes:

- `text`
- `extraction_summary`
- `document_segments`
- `layout`
- `tables`
- `formulas`
- `reading_order`

### Entity and relationship outputs
The system emits normalized `entities` and `relations` lists, each enriched with:

- canonical names
- ontology labels
- confidence scores
- stable IDs
- provenance / evidence metadata
- optional `unknown_candidate` proposals

### Ontology and schema outputs
The pipeline may include:

- `ontology_enrichment`
- `ontology_report`
- `ontology_proposals`
- `schema_proposals`

This gives the graph layer a forward-compatible schema evolution path.

## 3. Pipeline Metadata

The most operationally useful part of the output is `pipeline_metadata`.

It contains:

- `model_mode`
- runtime metadata
- `stage_status`
- `stage_outputs`
- `stages`
- loaded component flags for OCR, entity extraction, graph persistence, reranker, ontology enricher, and others

This allows UI clients to display live progress and understand which stages succeeded or were skipped.

## 4. How Outputs Are Persisted

All job artifacts are stored by [app/storage.py](app/storage.py) as JSON files under the configured jobs directory.

That means each job becomes a durable document containing:

- source payload metadata
- intermediate pipeline facts
- final results
- trace of the stage lifecycle

## 5. Frontend-Friendly Bundle

The normalized workflow bundle is generated by [app/pipeline/workflow_bundle.py](app/pipeline/workflow_bundle.py).

This bundle packages the job into a dashboard-friendly structure:

- overview cards
- timeline
- stages
- metrics
- entity and relation samples
- API catalog and diagnostic information

This separates the raw job JSON contract from the view-model that the frontend needs.

## 6. Advanced Output Blocks

In addition to the main graph outputs, the pipeline may return advanced analytics blocks such as:

- `advanced_semantic`
- `advanced_graph`
- `advanced_llm`
- `anomaly_detection`
- `rul_prediction`
- `root_cause_analysis`
- `failure_prediction`
- `advanced_graph_embeddings`
- `advanced_clustering`
- `advanced_lessons_learned`

These are produced by the advanced pipeline stage suite and make the system suitable for industrial reasoning, forecasting, and maintenance intelligence.

## 7. Output Summary

The output model is deliberately broad:

- low-level extracted facts
- high-level reasoning artifacts
- ontology-aware normalization
- graph persistence signals
- advanced analytics blocks

That broadness is the strength of the system: the same job can serve graph storage, frontend dashboards, RAG, and Copilot-style reasoning.
